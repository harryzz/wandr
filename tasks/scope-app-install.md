# Scope: app installer (+ thin loader) — the multi-component package boundary

> Preparatory analysis, 2026-05-26 (revised from "scope-app-loader"
> after the ship-wasm/cache-cwasm correction). Carves the **installer**
> and **loader** boundaries `post-art-roadmap.md` §7 (revised) calls
> for. The implementation lives in a future numbered task once this
> scope is accepted; this doc is the why + the contract.

## Why this is "installer," not just "loader"

The original framing was wrong. Apps ship `.wasm` (portable component
bytes); the per-device AOT `.cwasm` is a **cache**, regenerated by the
runtime. That's a direct parallel to Android's APK → dex2oat → `.oat`
in `/data/dalvik-cache/`: bytecode ships, native code is per-device.

`wasmtime::Engine::precompile_component(bytes) -> Result<Vec<u8>>`
(stable in wasmtime 44, already pinned) is the one-call API. On-device
Cranelift AOT works today; it's the same compilation path our
`wasmtime compile` CLI uses on the dev machine.

So there are **two** boundaries to draw, not one:

| Boundary | What it does | Cost today |
|---|---|---|
| **Installer** | Read `package.toml` → verify world + signature → copy `.wasm`s + assets to install dir → `precompile_component` each → write cache → stamp cache-key → register | **all new code** |
| **Loader** | Look up app-id → re-verify cache-key (re-precompile if stale) → `Component::deserialize_file` cwasm → return `LoadedApp` | thin layer over current `deserialize_file` + `instantiate` |

The dev workflow (CLAUDE.md "Build pipeline") sidesteps both — it
pre-compiles `.cwasm` on the dev machine and `adb push`es it to
`/data/local/tmp`. That stays as-is; the installer is the
non-developer path.

## Why now

`post-art-roadmap.md` §7.6 (revised): carve the installer + loader
boundaries now even though today's implementation is a hard-coded
`Component::deserialize_file`. The §9 (resolved 2026-05-26) rule:

> Keep the app-loader.rs and arbiter behind a boundary that does
> not bake in in-process assumptions, so the Hybrid (zygote-style)
> migration stays cheap.

Same boundary, same forcing function. Two near-term levers either of
which could land this year:

- **A second guest app** exercises multi-app: lifecycle arbitration,
  focus routing, per-app HostState, per-app cache dir, AOT-cache
  invalidation per package. Today's call sites assume one.
- **The Q5b signing decision** (open). When the format gets picked,
  verification belongs in the installer. Today there's no installer
  to put it in.

Neither is imminent. But the bounded cost now scales linearly with
caller count and package count once multi-app starts.

## Current state (what gets refactored)

Two call sites today, both inlining the same `Component::deserialize`
→ `SkikoUi::instantiate` pattern with subtly different cwasm-candidate
searches:

| File | What it does |
|---|---|
| `wart-host/src/lib.rs:117–141` (NativeActivity / winit path) | Tries cwasm filesystem candidates (`/sdcard/Download/...`, app-external-files dir), falls back to APK asset `skiko-component.cwasm`. Calls `Component::deserialize_file` or `Component::deserialize(bytes)`. Calls `SkikoUi::instantiate(&store, &component, &linker)`. |
| `wart-host/src/standalone.rs:55–70` (post-ART standalone path) | Calls `Component::deserialize_file(&engine, "/data/local/tmp/skiko-component.cwasm")` directly; falls back to `run_test_loop` if absent. Calls `SkikoUi::instantiate`. |

Both also build `HostState` inline and run
`wasmtime_wasi::p2::add_to_linker_sync` + `SkikoUi::add_to_linker`.
Engine is centralized (`App::make_engine()` — fine as-is).

Neither call site touches `precompile_component`. The cache layer
doesn't exist; today's `.cwasm` is whatever the dev pushed.

## End state (what the caller sees)

### Standalone / NativeActivity path (loader-only — no behaviour change)

```rust
let loader = app_loader::default_for_target();
let app = loader.load(&engine, AppRef::default_dev())?;   // today: SingleCwasm; tomorrow: by app-id
let bindings = app.instantiate(&mut store)?;
```

### Installer path (new code, separate entry point — not in the hot loop)

```rust
let installer = app_installer::default_for_target();
let install = installer.install(&engine, PackageBundle::from_dir(&path))?;
// install.app_id, install.version, install.install_dir
//   — register with package db once that exists
```

The loader knows nothing about `package.toml` directly; it consumes
the install-dir layout the installer writes. Today the install-dir is
synthetic (the dev shortcut: a single `.cwasm` at the legacy path
counts as an install of app-id `"_dev_"`, version `"0"`); the dev
workflow still works without touching it.

## Cache key + invalidation

`cache-key.toml` per install dir:

```toml
wasmtime_version = "44.0.0"
engine_config_hash = "sha256:…"          # over wasm_gc/function_references/exceptions/stack-sizes/...
[components]
ui     = { wasm_sha256 = "…", cwasm_sha256 = "…" }
logic  = { wasm_sha256 = "…", cwasm_sha256 = "…" }
```

The loader re-verifies on each launch. If any field has drifted (host
upgrade, manifest mutation, file corruption), re-precompile the
affected components and re-stamp. Otherwise just deserialize the
cached cwasm — the common path.

`engine_config_hash` is over the `wasmtime::Config` fields
`App::make_engine` sets (currently: `wasm_component_model(true)`,
`wasm_gc(true)`, `wasm_function_references(true)`, `wasm_exceptions(true)`,
`async_stack_size(8 MB)`, `max_wasm_stack(4 MB)`). Adding any new
config flag (e.g. `epoch_interruption(true)` for task 23) flips the
hash and triggers cache rebuild — exactly the behaviour we want.

## What stays out of scope (explicit non-goals)

These would inflate scope past "carve the boundary":

- **`link.wac` parsing / multi-component instantiation.** Today's
  guest has one component; the installer copies bytes, the loader
  deserializes one entry. The wac graph wiring is for when ≥2
  components actually ship.
- **`wkg` / Warg integration.** §7.4: wkg is pre-1.0; don't pick a
  transport yet. The installer's input is a directory bundle on
  disk — no opinion on how it got there.
- **Signing (Q5b).** Open. Hook in the installer
  (`fn verify_signature(bundle: &Bundle) -> Result<()>`) returns
  `Ok(())` until the format is picked.
- **A real package DB.** A flat directory `/data/wart/apps/<app-id>/`
  is the registry; no SQLite, no index file. Listing the dir is
  enough until multi-app makes that painful.
- **Update / rollback.** Side-by-side install
  (`/data/wart/apps/com.example.demo/{1.2.0,1.2.1}/`) is naturally
  supported by the layout; *atomic switch* + *rollback policy* is
  separate work.
- **Hot reload.** None.
- **`HostState` refactoring.** Loader returns `LoadedApp`; HostState
  is still built by the caller. Splitting `HostStateFactory` out
  belongs with the Hybrid `fork()` work.

## Steps (when the numbered task starts)

1. **Add `src/app_loader.rs`** with the trait + `LoadedApp` + `AppRef`
   enum + `WartLoader` (Installed path stubbed, Dev paths implemented).
   No callers touched.
2. **Refactor `standalone.rs`** to use the loader (only `AppRef::DevCwasm`).
   Smallest blast radius. Device-verify.
3. **Refactor `lib.rs`** (NativeActivity) to use the loader (DevCwasm +
   DevAsset). Verify APK still boots.
4. **Add `src/app_installer.rs`** with `AppInstaller` trait + `WartInstaller`
   skeleton: directory walk, copy `.wasm`s, call
   `Engine::precompile_component` per component, write
   `cache/<name>.cwasm` + `cache-key.toml`.
5. **Hook `AppRef::Installed`** in `WartLoader`: cache-key re-verify,
   re-precompile-if-stale, deserialize. Now we can install a synthetic
   single-component package and load it through the real path.
6. **Smoke**: a tiny synthetic `.warpkg` (one component, no link.wac)
   installs to `/data/wart/apps/_smoke_/0.0.1/`, loads, renders.
   Doesn't replace the dev workflow — just proves the real path
   compiles + runs end-to-end.

Steps 1–3 = the loader half (~1 day, mechanical).
Steps 4–6 = the installer half (~1–2 days, new code + on-device
`precompile_component` benchmark for the cache-rebuild UX).

Total ~2–3 days.

## Verification

- `bash scripts/standalone-launch.sh` brings up the dev runtime;
  UI renders + types as before. Loader path exercised; installer
  bypassed.
- `bash scripts/deploy.sh` (NativeActivity APK) still boots.
- Smoke install: shipping a one-component `.warpkg`,
  `wart-host --install /tmp/foo.warpkg` writes
  `/data/wart/apps/com.example.foo/0.0.1/`; running
  `wart-host --standalone --app com.example.foo` loads via
  `AppRef::Installed` and renders.
- Re-running the install with a manifest mtime bump triggers
  cwasm regeneration (verify by mtime on `cache/*.cwasm`).
- Re-running with no change skips precompile (cache hit).
- `git grep -nE "Component::deserialize|Component::from_file|SkikoUi::instantiate"`
  shows hits **only** inside `app_loader.rs` / `app_installer.rs`.
